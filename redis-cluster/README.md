在纯‌一主二从‌的基础主从复制架构下，没有哨兵或集群的自动故障转移能力，节点宕机的影响完全取决于故障节点的角色，结果差异非常明确。

🔴 主节点（Master）挂掉的后果
‌写操作完全中断‌：整个系统没有可写入的主节点，所有写请求直接报错或超时，业务无法写入新数据。
‌读服务部分保留‌：两台从节点仍正常运行，可继续对外提供读服务，已同步的历史数据不会丢失。
‌无自动故障转移‌：系统不会自动把某台从节点晋升为主节点，必须人工介入操作才能恢复写能力。
‌数据一致性风险‌：主节点宕机前最后一批异步同步的写操作，可能还没来得及推送到从节点，导致主从数据存在短暂不一致。
🟡 单台从节点（Slave）挂掉的后果
‌几乎无核心影响‌：剩下的1台从节点和主节点完全正常运行，读写服务不受任何中断。
‌读能力小幅下降‌：原本分流到故障从节点的读请求，会被负载均衡转发到剩余节点，整体读QPS上限略有降低。
‌数据冗余度下降‌：原本2份副本变成1份，数据备份的容错能力暂时降低，仅剩1台从节点承载全量副本。
‌故障恢复自动重连‌：故障从节点重启后，会自动向主节点发起同步，先执行增量同步（若积压缓冲区未溢出），快速补全宕机期间缺失的数据，无需人工干预。
🟠 两台从节点同时挂掉的后果
‌写服务不受影响‌：主节点仍可正常处理所有写请求，不会因为没有从节点而停止写入。
‌读能力完全集中‌：所有读请求全部压到主节点上，原本的读写分离架构失效，主节点的CPU和内存压力会明显上升。
‌主节点写保护触发‌：如果配置了 min-replicas-to-write 参数，主节点检测到可用从节点数不足2时，会主动拒绝新的写请求，避免数据单点丢失。
‌数据完全无副本‌：此时主节点是唯一的数据载体，一旦主节点再发生宕机，所有数据将直接丢失。
🛠️ 人工恢复操作指南
‌主节点宕机恢复‌：选一台数据最完整的从节点，执行 slaveof no one 命令将其晋升为新主节点，再把另一台从节点配置为新主的从节点，最后通知业务方切换写地址。
‌单从节点宕机恢复‌：重启故障从节点，确认配置文件里的主节点地址正确，启动后会自动完成全量/增量同步，无需额外操作。
